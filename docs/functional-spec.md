## 1. Product Vision

A cross-platform desktop app (macOS + Windows) providing a **Word-like writing and reviewing experience for documents** — the Markdown family plus plain-text `.txt` in v1 (D27/FR-ED-9). Markdown remains the format the rest of this specification is written against. Each document file is always its own source of truth; everything the app adds (comments, tracked changes, skills, workflows) lives in portable, repo-owned formats so the user is never locked into Cowrite.

### The three pillars (CJ, 2026-07-04)

1. **Brainstorm → Revise → Skill-based review.** The user brainstorms with an LLM that is backed by Claude Code and aligned to a repo (so skills apply and can be built over time). The LLM can take a draft or the conversation itself and produce a revision. The document can then get a skill-based review (e.g., staged review workflows).
2. **User comments → LLM addresses.** The user adds comments to the document and can have the LLM address them.
3. **Collaborative review.** Other people review the document and add comments; the user addresses them personally or delegates to the LLM.

### Reference example repo

`biblical_writing` (local: `C:\Users\williacj\github\biblical_writing`) is the canonical example of the target working style:

- `claude_skills/<name>/SKILL.md` + `references/` — real Claude Code skills with activation triggers, style rules, evaluation rubrics.
- `references/lessons-learned-log.md` inside skills — the LLM distills lessons from working sessions back into the skill (skill-building loop already exists in practice).
- `workflows/*.md` — staged, **gated** review/development processes that orchestrate skills sequentially (e.g., sermon-review-workflow: biblical-accuracy gate → listener review → grammar), with structured output formats and severity ratings.
- `claude.md` — repo-level canonical style rules that skills defer to.

An unquoted message carries no quoted-selection envelope — amended by D30/FR-CHAT-4 (CJ, 2026-09-02), under which every message also carries open-document context, so an unquoted prompt is no longer the user's bare text. **`quoted_selection` is size-bounded at 1 MiB, measured as the UTF-8 byte length of the quoted text itself — never UTF-16 code units, characters, or the serialized envelope's JSON-escaped form (D32, CJ 2026-09-03).** `quoted_text` is carried whole when that length is 1,048,576 bytes (1024 × 1024) or fewer, and withheld entirely — never a prefix, an elision, or a summary — when it is greater; a partial quote that reads as whole is worse than an absent one, the same reason D31 forbids truncating FR-CHAT-4's `content` and FR-X-5 forbids a silent no-op. Over the bound, the entry still carries `document_path` (or the pathless form below) and `anchor` but not `quoted_text`, plus exactly one fixed statement naming the *quote itself* as its subject, never the document generally, so it cannot be read as a statement about that same document's separate FR-CHAT-4 `open_documents` entry, which may co-list it for an unrelated reason and on its own separate terms: **(q)**, for a path-bearing entry, that the selection was too large to include and so was not supplied, and that `document_path` is the only route the agent has to this text — present exactly when the entry carries a non-null `document_path` and the selection is over the bound, absent otherwise; and **(q-pathless)**, for a pathless entry, that the selection was too large to include and so was not supplied, and that the document exists nowhere on disk, so there is no route to this text at all — present exactly when the entry carries `document_path: null` and the selection is over the bound, absent otherwise. An at-or-under-bound entry, pathless or not, carries `quoted_text` and no statement, exactly as before this amendment; the presence of a `quoted_selection` envelope carrying no `quoted_text` and a statement is what tells an over-bound quote apart from an unquoted message, which carries no `quoted_selection` envelope at all. **A quote's `document_path` may legitimately name a document that is not open**, so (q)'s promise is weaker than FR-CHAT-4's own over-bound statement makes for `content` — the agent may have no other route to that text at all, and (q) says only what is true rather than implying a fallback that may not exist. **`quoted_selection` also gains a pathless representation, mirroring FR-CHAT-4's `open_documents` convention exactly (D33, CJ 2026-09-03):** when the quoted document has no file, the envelope carries `document_path: null` and a `label` — the same name the document's tab shows, disambiguated the way the tab strip disambiguates it, so the same words identify it to the user and to the agent. `label` is present exactly when `document_path` is `null`; a path-bearing entry carries no `label` in any form, null or otherwise. The internal `untitled:<n>:` tab spelling is never sent as `document_path`, for FR-CHAT-4's own recorded reason: that spelling is itself a legal project-relative path (D21, 2026-08-28 clause), and no consumer of the envelope could tell it apart from a real one. **This makes quoting a real route to an untitled document's content — the ruled consequence of D33, not a side effect of the schema.** FR-CHAT-4 names quoting as the route out of its own background-dirty-tab rule ("unless its content is supplied through an explicit quote") and, until D33, stated that this route did not exist for an untitled document, because quoting is wired only for the active tab and an untitled document renders as `UntitledDocument`, which offers no quote affordance today. This requirement now admits the envelope shape that route needs; it does not itself build the affordance — the quote-capture wiring and the submit path that carries it follow under a later implementation card (#2304), not this one. **Where D32 and D33 combine — an over-bound quote of a document with no file — the entry carries `document_path: null`, `label`, and `anchor`, no `quoted_text`, and statement (q-pathless) alone:** it names both facts truthfully in one statement rather than two, because there is no file at any path for the agent to fall back to. (#714, #2249, #2239, D21, D12, D30, D31, D32, D33, FR-ED-8, FR-CHAT-4, FR-X-5, UX Principle 6)
- FR-CHAT-4 (MUST): **Every agent run the app submits names the documents open in it, and carries the live buffer of the one being edited — or says that buffer was too large to carry (D31).** A chat turn, a single "Address with AI" run, and a batch address run alike carry one versioned structured reference-data envelope — `cowrite_context_version: 1`, `kind: "open_documents"`, a sibling of FR-CHAT-3's `quoted_selection` under the same convention (adding a kind does not bump the version) — stating which document the user is looking at, which others are open, and what the edited buffer actually says — or, where that buffer is over the size bound below, that its text was not supplied. **Identity and dirty state for every open document (D30):** each entry carries `path`, the document's project-relative forward-slash identity spelled exactly as that run's operation target is spelled (D21) — never an absolute path, never a path outside the project root — and `unsaved`, present on every entry. **`unsaved` means the buffer is not represented by a file on disk.** That is its *conceptual* definition; its *operative* source differs by document, and both limbs are stated here because a literal reading that lands on `TabRecord.dirty` alone gets the second one wrong silently. **For a document that has a file and a saved baseline, `unsaved` is FR-ED-3's dirty flag** — the buffer differs from the baseline it was last saved or loaded at — and **never a live comparison against the bytes on disk**, a comparison the app deliberately does not make: it keeps the dirty baseline and FR-ED-7's external-change baseline apart on purpose, because a normalizing save diverges them (FR-ED-2; `savedContentRef` `@anchor:editor-shell-saved-content-ref` and `diskContentRef` `@anchor:editor-shell-disk-content-ref` in `src/editor/EditorShell.tsx`, whose own comments record why they are kept apart). The corner that limb decides: a tab the user has not typed into whose file changed underneath it is **`unsaved: false`** — it carries no `content`, and the agent reads the fresher file itself, which is right there, because the buffer is the copy that is behind and FR-ED-7's divergence is still unresolved. **For a document with no file and no saved baseline — an untitled or scratch document (D12, FR-ED-8) — `unsaved` is `true` by construction, irrespective of `TabRecord.dirty`**, which is `false` for such a tab by ratified design: that flag drives FR-ED-3's save guard, and there is nothing to save this one *to* (CJ, 2026-08-12). Deriving `unsaved` from the dirty flag alone would ship an untitled document as `unsaved: false` and so drop its `content`, deleting the only route to a document this requirement calls reachable no other way — and every test would still pass. **Content for the active document, while it is dirty and within the size bound:** when `active.unsaved` is true *and* the snapshot is within the bound stated next, the active entry also carries `content`, the exact submit-time snapshot of that in-memory buffer — byte-for-byte as the user has it, neither normalized nor truncated (the prompt is delivered on stdin precisely so a reference payload larger than the OS command-line limit still arrives whole, FR-CHAT-3). `content` appears on no other entry and is absent — not null — whenever the active document is clean **or its snapshot is over the bound**, so an ordinary clean turn sends identity alone and the agent reads the file itself (D4). **The bound is 256 KiB, and a snapshot is sent whole or not at all (D31, CJ's ruling of 2026-09-02).** `content` is carried when the snapshot's **UTF-8 byte length is 262,144 bytes (256 × 1024) or fewer**, and withheld entirely when it is greater — the bound is stated as a byte count, and as at-or-under versus over, because "256 KiB" against an in-memory UTF-16 string is ambiguous and would otherwise be guessed. The measure is the buffer's own bytes as they would be sent, UTF-8 encoded — never UTF-16 code units, never characters, and never the serialized envelope around the buffer, whose JSON escaping would make the effective bound vary with the text's punctuation. That is the measure and the boundary the product's existing session-durability cap already uses (`UNSAVED_CONTENT_CAP_BYTES` `@anchor:session-unsaved-content-cap-rust` in `src-tauri/src/store/tab_session.rs`, mirrored as UTF-8 bytes by `SESSION_UNSAVED_CONTENT_CAP_BYTES` `@anchor:session-unsaved-content-cap-ts` and `exceedsSessionContentCap` `@anchor:exceeds-session-content-cap-fn` in `src/stores/tabs.ts`), but this is **a different bound answering a different question, and neither derives from the other** — 256 KiB bounds what one turn re-sends while a buffer is dirty; 2 MiB bounds what a session snapshot can durably hold — so the two stay two constants and no implementation collapses them into one. **Truncation is not what the bound does, and stays forbidden:** over the bound the app omits `content` entirely and says so; it never sends a prefix, an elision, or a summary, because an agent handed the first 256 KiB of a manuscript with no marker reads a partial document as if it were whole (FR-X-5). **The bound is applied per submission, to that submission's snapshot**, at the same capture boundary as the rest of the envelope — so a document may carry `content` on one turn and the over-bound statement on the next as the user types across the boundary, and nothing about an earlier turn's snapshot is cached, sticky, or carried forward. It bears on the active entry alone, since no other entry carries `content` in any case. **Submission never force-saves** to produce a snapshot (FR-ED-2 autosave is unaffected and unaccelerated). **A dirty background tab contributes identity and dirty state only**, unless its content is supplied through an explicit quote (FR-CHAT-3) or a later explicit attachment mechanism. **Which text is current is stated by the app, in the payload.** The agent has the repo as cwd and can read the file itself, so for one document it may hold two texts; this requirement settles which is current and obliges the **app** to say so, because the app can only emit — what an agent then does with a correctly stated payload is its behaviour, which no requirement on the app binds and no test of the app asserts. The reference-data block therefore carries, as fixed text emitted with the envelope: **(a)** for an entry carrying both a `path` and `content`, a statement that the `content` is that document's current text and that the file at its `path` is behind it — present exactly when an entry carries both, absent otherwise; **(a-pathless)** for an entry carrying `content` with a `null` `path`, a statement that the `content` is that document's whole text and that it exists nowhere on disk, so there is no file to read for it — present exactly when an entry carries both of those, absent otherwise; **(b)** a statement that a listed document whose entry offers neither a readable `path` nor `content` was not supplied and cannot be read — present exactly when such an entry is listed *for a reason other than the size bound*, absent otherwise; **(c)** for a path-bearing entry whose `content` was withheld because its snapshot is over the bound, a statement that the document's current text was too large to include and so was not supplied, and that **the user's unsaved changes are not in the file at its `path`, which is the only route the agent has to this document** — present exactly when such an entry is listed, absent otherwise; and **(c-pathless)** for an over-bound entry whose `path` is `null`, a statement that the document's current text was too large to include and that the document exists nowhere on disk, so there is no file to read for it — present exactly when such an entry is listed, absent otherwise. **(c-pathless) is scoped to this entry's own withholding, not to the turn as a whole:** it claims that the text was too large to include and that no file backs this entry, never that no route to the document's text exists anywhere in the turn — a co-riding quote of the same document may carry that same text under FR-CHAT-3's own separate bound (D32/D33), each statement standing, as FR-CHAT-3 puts it for the reverse case, "on its own separate terms." **Exactly one of (a) and (a-pathless) accompanies any entry that carries `content`** — never both, and never neither — because a pathless entry has no file for (a) to be true of. **Of the withholding statements, exactly one accompanies each entry this requirement gives a statement to, and the set is disjoint but deliberately not exhaustive over the entries:** an entry with `path: null` and no `content` takes (c-pathless) when it is the active entry over the bound and (b) otherwise, and the active entry over the bound *with* a path takes (c). **A path-bearing entry that carries no `content` for any other reason receives no statement at all**, exactly as before this amendment — a clean tab withholds nothing, since the file is the document; and a dirty background tab's identity plus `unsaved: true` is the whole of what the ratified background rule supplies for it. Nothing here requires a statement where the merged requirement emits none, and a rule read as covering *every* entry whose text was withheld would demand one for a dirty background tab, which is not this amendment's to change. **(c) and (c-pathless) name the active document, and must say so.** (a), (a-pathless) and (b) each identify their subject by field pattern, and those three patterns partition the entries they describe; neither over-bound statement can be identified that way, because **(c)'s shape — a `path`, `unsaved: true`, no `content` — is also every dirty background tab's**, and **(c-pathless)'s shape is identical to (b)'s**, with which it can co-occur in one payload (an over-bound active untitled document beside a background untitled tab). A statement that named its subject by shape would therefore be false of co-listed documents, which is the FR-X-5 dishonesty the bound exists to avoid. Only the active entry can be over-bound, so naming the active document is what makes each of the two true of exactly the entry it describes. Whether that binding is achieved by naming the active document in envelope-level text or by attaching these two statements to their entry is an implementation's to choose; what this requirement forbids is a statement whose subject the payload does not determine. The two routes do not cost the same, and the difference is named rather than left to be discovered: the envelope-level route needs no schema change and is fully specified here, while attaching a statement to its entry adds a field to the entry shape — a change to the envelope's schema, which this envelope's "adding a kind does not bump the version" allowance does not cover. Whether such a field bumps `cowrite_context_version` is not settled here and is not an implementer's to assume. (b) does not widen to cover the bound: it reads *not supplied and cannot be read*, which is flatly false of a path-bearing over-bound entry — that file is right there and readable, merely behind — and on a pathless one it is true but silent about the fact that the app **has** the current text and chose not to send it, which is the whole of what the bound introduced. **No entry carries two of the five, and no statement names a size, a byte count, or a proportion** — what the payload discloses about a document's text is *whether* it went, never how much of it did. **(c) is worded to be true without the app reading the disk:** the app deliberately makes no live comparison against the bytes on disk, as `unsaved` above says, so no statement may assert that a file exists at that path or what it now holds — (c) names the path as the only route the agent has and says the user's unsaved changes are not in it, which stays true whether that file is current, stale, or gone. All five are descriptions of the payload, never instructions to the agent: the block is labelled reference data and not instructions (FR-CHAT-3), and this requirement does not change that. Their presence and absence is what FR-CHAT-4 requires and what a test asserts. None of it authorizes a write — the snapshot is never a licence to save it back, and changes still arrive as tracked changes (D21, FR-AGENT-2). **The active document is `active`** — one entry, or `null`; **every other open tab is an entry of `also_open`**, in the app's own tab order. No document appears twice, and a document that is in a review set or is an operation target but is not open in a tab is not listed. **A document with no file has no path:** an untitled or scratch document is listed with `path: null`, `unsaved: true`, and `label` — the same name its tab shows, disambiguated the way the tab strip disambiguates it, so the same words identify it to the user and to the agent. `label` is present exactly when `path` is `null`; a path-bearing entry carries no `label` in any form, null or otherwise, and is named by its path alone. An untitled document's internal tab identity is never sent as a `path`, because that spelling is itself a legal project-relative path (D21, ratified 2026-08-28) and neither the agent nor a consumer of the envelope could tell the two apart. It is `unsaved: true` under the second limb above, so **an active untitled document carries `content` whenever its snapshot is within the bound** — it is reachable no other way — and the statement accompanying it is (a-pathless), never (a). **Where "reachable no other way" meets the bound, the outcome is ruled rather than left to be discovered (CJ, 2026-09-02): an active untitled document over the bound carries no `content` and has no `path`, so this entry itself supplies no route to its current text.** It is listed with `label`, `path: null`, `unsaved: true`, and statement (c-pathless), which says exactly that — scoped to this entry alone, per (c-pathless)'s own wording above — and does not pretend some file could be read instead; it is not truncated, for the reason above. **The bound is applied uniformly and is not waived for it**, on CJ's two stated reasons: the per-turn cost the bound exists to hold is identical whether or not the buffer has a file, and waiving it would make the *exceptional* path the unbounded one. **The route out is the user saving the document**, which gives it a path and so gives the agent a file to read without the buffer having to ride the turn — and, once saved, a stable path for FR-CHAT-3's quote route too. **This clause is unchanged by D33** (CJ, 2026-09-03): saving is still what gives *this* clause's file-read route to the agent, but it is no longer what unlocks quoting in the first place — FR-CHAT-3's `quoted_selection` gains a pathless form of its own, so once #2304 wires the affordance, an unsaved untitled document's text is quotable without saving it first. **An active untitled document is therefore in exactly one of two conditions, and no other:** within the bound, carrying `content` with statement (a-pathless); or over the bound, carrying no `content` with statement (c-pathless). It is stated as two conditions so a downstream surface can key off the second directly rather than inferring it from a rule about the first. **An untitled document in a background tab offers neither a readable `path` nor `content`:** it is named by `label` alone and its text is not supplied — under the background rule and not under the bound, which is why statement (b) is what says so. **Quoting was not a route out of that for an untitled document — until D33 (CJ, 2026-09-03) ruled the opposite; amended here in place, per this document's own convention for a ratified requirement absorbing a later decision (D30/D31 on this same FR-CHAT-4).** The ratified "unless explicitly quoted or attached" clause holds for path-bearing tabs; an untitled document has **no quote affordance today** — it renders as `UntitledDocument`, which has none, and quoting is wired only for the active tab (`TabbedEditorProps.onQuoteSelection` in `src/editor/TabbedEditor.tsx` `@anchor:tabbed-editor-props-on-quote-selection`, and the render-time wiring that passes it only to the active tab's `EditorShell`) — so as of this text no such route is built. **D33 rules that the gap closes rather than stays permanent: FR-CHAT-3's `quoted_selection` gains a pathless `document_path: null` + `label` form for exactly this case, making quoting a real, ruled-for route to an untitled document's content.** This requirement records that ruled consequence; it does not itself build the affordance — the quote-capture wiring and the submit path that carries it follow under a later implementation card (#2304), not this one. Until that wiring lands, the route that does exist is the user making the document active — for which the rule above guarantees `content` and statement (a-pathless) only while the resulting snapshot is within the bound; over the bound, activation alone still yields no `content` and statement (c-pathless), and saving the document remains the only route out of that case. **With nothing open the envelope is still sent**, carrying `active: null` and an empty `also_open`: the agent is told there is no open document rather than left to infer it from silence, and repo-level chat continues unchanged (D4, FR-CHAT-1). The envelope is captured when the request is submitted, at the same boundary as the D21 operation target, so both the set and the snapshot are what the user was looking at when they pressed Send — not what happens to be open, or typed, when a queued run is finally dequeued (FR-AGENT-7). **The envelope grants no authority:** it reports clause (1) of D21's union only, it is neither the protected set nor the operation-target set, and naming a document in it never makes that document an operation target, authorizes an edit to it, or changes its protection — an untitled document named as `active` still has no operation target, exactly as D21 already says. Clause (1) is read as D21's *conceptual* scope, which is why an untitled document is listed here while the backend's *operative* open-tab set excludes it (D21's 2026-08-28 clause; `TabbedEditorHandle.openDocuments`' own doc comment in `src/editor/TabbedEditor.tsx` `@anchor:tabbed-editor-open-documents-doc`, which says exactly this) — the two are different questions, and D21 says so. A turn that also carries a quoted selection carries both envelopes, the ambient `open_documents` one first and the quote last as the more specific referent; the quote is never suppressed, rewritten, or reconciled against the open set, and its own captured `document_path` may legitimately name a document that is not open. - FR-CMT-13 (MUST): Revision semantics — the thread shows the current body. Where the comment was published to a review (D20) or another actor has already replied, the card is marked **edited** with the revision time, for the same reason withdrawal leaves a placeholder: someone may have acted on the earlier text, and their reply must never appear to answer words that were never there. Prior bodies remain in the log because it is append-only, but Cowrite offers no version browser in v1 and no surface presents the edit history. **Withdrawal is terminal** — a revision never resurrects a withdrawn comment, whatever the arrival order of the two records (P5). (D24)
- FR-CMT-14 (MUST): Dismiss a thread — the document author can close any open thread with the outcome **dismissed**: *considered, and not accepted; nothing was changed.* It is offered on every thread whatever its provenance — the author's own comment, an agent finding (FR-REVIEW-2), a reviewer's comment — including a thread the agent has defended without editing (FR-CMT-4). An optional short note may accompany it and is **never required**. Dismissal is an appended event in the dismisser's own log recording their judgment; it removes, edits, or hides nothing another actor wrote, so it is triage and not moderation (D24). Reviewers resolve nothing and therefore dismiss nothing (FR-COLLAB-2). (D25, epic #1162)
- FR-CMT-15 (MUST): Dismissal is a closure **outcome**, not a second lifecycle — a dismissed thread is closed exactly as a resolved one is: it leaves the open count, is excluded from batch addressing (FR-CMT-5), is not among the comments the agent is offered for a document (TD-1), collapses in the timeline and comments column, and does not raise D18's unresolved-comment warning at review completion. What differs is only what it asserts: **no surface may render a dismissed thread as resolved, or count it among the addressed or fixed findings** of a review summary (FR-REVIEW-3). A thread has exactly one current closure outcome — resolution and dismissal are peers that never coexist, decided by the log's existing deterministic fold ordering (P5); this requirement invents no new tie-break. `reopen` inverts dismissal exactly as it inverts resolution (FR-CMT-3), so dismissal is neither confirmed before the fact nor separately undoable after it. (D25)
- FR-CMT-16 (MUST): Dismissal never decides agent work — it is refused, visibly and with a stated reason plus a route to the changes, while any linked tracked change is undecided (FR-CMT-7); it is **not** refused while an addressing run is in flight, on the same terms manual resolve is not (FR-CMT-21). No comment action decides, discards, or unlinks a tracked change in a protected document on the user's behalf (D21, FR-CMT-10), and refusal is never a silent no-op (FR-X-5). Rejecting a linked change and dismissing the thread are **two records that compose in that order**: rejection reopens the thread with per-change outcomes visible to the agent (FR-CMT-3/7), and the reopened thread may then be dismissed, the rejected change's outcome standing on its own in the change sidecar. (D25; **in-flight-run limb withdrawn by D29, ratified by CJ 2026-08-20** — that limb was inherited from FR-CMT-10's shape, whose reason is about *correction* rewriting the comment body, while closure changes no text and no anchor. In-flight status by itself adds no separate closure refusal. A run can already have delivered — J7 records `STOPPED — partial delivery`, and FR-AGENT-6's atomicity is about one delivery, not about the run — so any already-landed undecided linked change is caught by the limb above, which is unchanged in force and now binds **both** closure outcomes (FR-CMT-21).)
- FR-CMT-17 (MUST): Dismissal is published wherever resolution is — carried by the review sync under D20's standing consent with no per-item send — labelled as a dismissal and carrying its note where one was given. An external reviewer sees that the author declined the comment or finding, never that it was resolved. Dismissal is a **thread** outcome: on a thread carrying an agent defense (FR-CMT-4) it closes the thread and the defense remains visible; there is no dismissal of an individual reply. (D25, D20)
- FR-CMT-18 (MUST): The dismissal record is legible to whoever asks later, and v1 builds no consumer of it beyond re-delegation — a thread reopened after a dismissal carries that dismissal and its note to the agent, as a rejection does (FR-CMT-3/7), and a dismissed finding retains its severity and source skill (FR-REVIEW-2) so a later "distill lessons into skill X" affordance (FR-SKILL-3b) can find it without a migration. V1 adds **no** skill feedback loop, **no** suppression of a later run re-raising the same finding, and **no** dismissal analytics. (D25, D11)
- FR-CMT-19 (MUST): Reopen a closed thread — the document author may reopen a thread that a manual resolve, an automatic resolve (FR-CMT-3/7), or a dismissal (FR-CMT-14) closed. Cowrite offers the act on a closed thread only, in author mode only, and on a thread of any provenance (FR-COLLAB-2). A withdrawn comment is not a closed thread, and its placeholder offers no reopen. No reopen event restores a withdrawn comment in any arrival order (FR-CMT-13, P5). A reopen is an appended event in the reopener's own log, and it never removes or changes the closure it inverts (FR-COLLAB-9, P5). A reopen decides no agent work: it never accepts, rejects, or unlinks a tracked change, and decided changes stay decided (D21). The user reopens from the closed thread itself, with no reveal of the hidden set first. Cowrite does not confirm the act. (D28, ratified by CJ 2026-08-20; epic #1162)
- FR-CMT-20 (MUST): Reopen semantics — a reopen returns the thread to the open state for every purpose the closure removed it from. These purposes include the open count, batch addressing (FR-CMT-5), the comments the agent gets for the document (TD-1), and the collapsed set of closed threads. The thread shows the *reopened* condition, which a rejection (FR-CMT-3/7) and a hand reopen both produce. A reopen publishes where the closure it inverts published (D20), states the reversal there, and never erases the closure line. No Cowrite surface shows the author less of a thread's closure history than the external reviewer's copy of that thread shows. **That last rule binds only a reopen that inverts a recorded closure.** A rejection-driven reopen inverts no closure and shows no closure line. What the thread carries to the agent depends only on what closed it. A rejection carries the per-change outcomes (FR-CMT-3/7). A dismissal carries the dismissal and its note (FR-CMT-18). A hand reopen of a resolve carries nothing, and Cowrite records no reason and no note on the reopen act in v1. A reopened thread with no earlier delivery offers ordinary addressing (FR-CMT-2) and not re-delegation. A thread has one current closure outcome or none, and a reopen leaves none. A later closure is a new event, decided by the existing fold order (FR-CMT-15, P5). (D28, ratified by CJ 2026-08-20; epic #1162)
- FR-CMT-21 (MUST): Closure availability is one rule for both outcomes, and it binds the manual act only. The automatic resolution of FR-CMT-3/7 stays unchanged. (a) If any linked tracked change is undecided, Cowrite refuses both manual resolve (FR-CMT-1) and dismissal (FR-CMT-14). The refusal is visible and states its reason. It names the route: an accept resolves the thread (FR-CMT-3/7), and a reject reopens it for a later dismissal (FR-CMT-16, D21). (b) If an "Address with AI" run is in flight for the thread (FR-CMT-2), both outcomes stay available. The thread states the closure in place (FR-X-5). A delivery into a closed thread clears the closure, states the sequence, and lands the thread at *addressed — pending*, whichever outcome closed it. A closure never stops, cancels, or narrows a run. Neither condition refuses a reopen (FR-CMT-19). A refusal is never a silent no-op (FR-X-5). These rules keep one property: no closed thread holds an undecided linked tracked change, on either path. (D29, ratified by CJ 2026-08-20; epic #1162 — amends FR-CMT-16, and FR-CMT-10 for the correction half of the same phrase)
- FR-CMT-22 (MUST): **What `@` addresses, and what a token that addresses nothing does** — proposed 2026-09-08 by D34, not ratified. The namespace is a **positive set**: the repo's discovered skills (FR-SKILL-5) plus one reserved `@agent`. Nothing else resolves — no provider, no model, no human reviewer. A future addressable kind is admitted by amending this requirement, never by a token slipping past a list of what is forbidden. A skill's mention token is its discovered `name`, used verbatim; Cowrite normalizes nothing and mints no second identifier (D1, FR-SKILL-2). A token may carry only ASCII letters, digits, `-` and `_`. A discovered skill whose `name` carries anything else is not addressable by mention, and renaming it in the repo is the route out. Matching is exact, so `@Code-Review` does not address `code-review`. **A token that two or more discovered items would resolve to addresses none of them**, and the app says so where it lists skills (FR-SKILL-1). `agent` is reserved: a discovered skill of that name never shadows `@agent` and is unaddressable by the same rule. Only a token that resolves to exactly one addressee may be offered for completion. **A mention-shaped token that resolves to nothing is never a refusal and never a silent no-op** (FR-X-5, Principle 7). The post always succeeds and the body is recorded verbatim; Cowrite never rewrites, strips or withholds the user's own words. Where a posted body carries `@` followed by a token at a word boundary and that token resolves to no addressee, the thread names the token and states that it started no run. (D34, D1, FR-SKILL-1/2/5, FR-X-5, epic #2454)
- FR-CMT-23 (MUST): **Dispatch is a property of the post event, not of the text** — proposed 2026-09-08 by D34, not ratified. **One post starts at most one run.** A posted comment or reply whose body carries at least one resolving mention starts exactly one agent run for that thread. A post carrying none starts none and is an ordinary note (FR-CMT-1). **Several mentions in one post are all named to that one run.** A repeated mention of one addressee is named once. The app never sequences, prioritizes or composes the addressees — that is the agent's, exactly as FR-REVIEW-1 leaves workflow stages to it. **Only a post dispatches.** An FR-CMT-12 revision that adds or changes an `@` never dispatches, and is refused mid-run in any case (FR-CMT-10). A withdrawal (FR-CMT-8/9) never cancels a running run (D21, D25). **Every run started from a thread has exactly one post that started it.** FR-CMT-5's collection-level batch starts from its own surface and posts nothing (FR-CMT-24). **A post made while a run is in flight is never refused, and its run queues** (FR-AGENT-7). Appending a reply changes no text a submitted run already captured, so correction's reason for failing closed (FR-CMT-10) does not reach it. **A reply posted while a run holds the thread is not in that run.** Whether a surface must say so is `ux-design.md`'s open UXR-Q25.2, unchanged by this model. (D34, D21, D25, FR-AGENT-7, FR-CMT-1/5/8/9/10/12, FR-REVIEW-1, FR-X-5, epic #2454)
- FR-CMT-24 (MUST): **What a mention binds, what `@agent` is, and what the shortcut does** — proposed 2026-09-08 by D34, not ratified. **A skill mention names that skill to the run and binds nothing else.** It is prompt-level: the app names the skill and the agent interprets it (FR-REVIEW-1). A mention does not mint, select or switch a session (D4). It does not select a provider or a model — FR-X-7's per-project default governs every run, and a skill's Claude-specific `model`/`agent` frontmatter stays ignored-gracefully (FR-PROV-1). It does not change the protected set or the operation target (D21, FR-AGENT-2), and it does not change what the run may deliver (D8, FR-CMT-2). **`@agent` names no skill** — it is the unskilled run FR-CMT-2 starts today, and it is not FR-X-7's provider default under another name. **`[Address with AI]` inserts `@agent` and posts**, never a last-used persona; the app stores no sticky persona. Because the shortcut inserts the mention rather than dispatching invisibly, what was sent is visible in the posted body. **The batch surface is unchanged** (FR-CMT-5): `Address all…` gains no persona choice and starts an unskilled run, so there is no precedence rule to write. A swept thread's own mention is not discarded — it is body text, and rides to the run as part of the thread (PR #2448 Q4). (D34, D4, D8, D21, FR-AGENT-2/7, FR-CMT-2/5, FR-PROV-1, FR-REVIEW-1, FR-SKILL-1/5, FR-X-7, PR #2448, epic #2454)
- FR-CMT-25 (MUST): **FR-CMT-10's correction bind reaches the replies, not the root alone** — proposed 2026-09-08 by D34, not ratified; the reading PR #2448 routed to the PM. FR-CMT-10 already says *the thread*. This states the reading so no implementer has to guess it, and so the guess does not land on the permissive side. Under this model the run carries the whole thread (PR #2448 Q4) and the dispatching reply is the request. Revising or withdrawing a reply mid-run is therefore the same hazard as revising the root. Nothing is amended. **It binds correction only.** Closure stays refused at no rung (FR-CMT-21, D29). A post is never refused for a run in flight (FR-CMT-23). No comment action decides, discards or unlinks a tracked change (D21). It changes no requirement's force and no card's state, and it settles nothing about what the agent may read of its own earlier work (#2455). (D34, D21, D29, FR-CMT-2/8/9/10/12/21, PR #2448, #2455, epic #2454)

- FR-COLLAB-2 (MUST): Cowrite reviewer mode — a git-free experience: sign in (device flow), accept-invited repos listed, auto-clone to a managed location, open document, read Word-style redline with attribution, add/reply-to comments, resolve nothing (author owns resolution). (D9)
- FR-COLLAB-2b (MUST): Reviewer suggestions: select text → propose replacement wording, delivered as a structured suggestion-comment; author/AI applies it as a tracked change attributed to the reviewer. Reviewers never modify document files directly. (D19)
- FR-COLLAB-3 (MUST): Author editing remains live during an active review; author/AI changes and comment replies sync to reviewers. (D9)
- FR-COLLAB-4 (MUST): Reviewer comments sync into the author's unified comment system with provenance; author addresses personally or via "Address with AI" (D8), including published AI defenses.

- FR-COLLAB-9 (MUST): Comment sync never loses a comment: sidecar storage is designed so concurrent additions from multiple machines merge automatically (e.g., append-only per-author records); sync is on-save/on-focus with manual refresh; conflicts must never require the user to resolve raw JSON. **A deliberate authored correction (FR-CMT-8 withdrawal, FR-CMT-12 revision) is not a loss under this rule** — it is itself an appended record that merges and converges like any other comment event, and removes no stored record. (finding #3; correction clause D24 — a **scope clarification, not a relaxation**: this requirement's subject was always *sync*, and the rest of its sentence is entirely about concurrent merge and conflict handling. It never governed what an author may deliberately do to their own words. CJ, 2026-08-05.)

### 3.5 Editor core

- FR-ED-1 (MUST): WYSIWYG + raw source view toggle; CommonMark+GFM; round-trip fidelity is P0 **including YAML frontmatter**. (D13)
- FR-ED-2 (MUST): Autosave (configurable, default on) + manual save/Save As; atomic writes; LF normalization with CRLF warning. (D13)
- FR-ED-3 (MUST): Multi-tab, per-project session restore incl. unsaved content, dirty-close guards, undo/redo, spellcheck, inline rename. On restoring a legacy tab whose path is now an unsupported document type, an explicitly retained unsaved buffer (including a present empty string) must survive exact and become an editable untitled recovery document labeled by its former project path; until that conversion is durably persisted, the legacy snapshot remains the recoverable copy. A failed conversion must not delete the only buffer or mount an unsupported editor. An omission marker alone never supplies missing text. J2's editable untitled recovery document distinguishes a live buffer above the 2 MiB per-tab session cap from a buffer the session omitted before relaunch: the first remains present but is not session-durable, while the second restores empty with an explicit standing loss state. The session persists `unsaved_content_omitted`, `loss_notice_collapsed`, and a stable duplicate displaced-label ordinal as authoritative facts; `recovered_from` plus null content is only a bounded legacy normalization at the Rust storage boundary. Closing always asks with copy and destructive treatment matched to what would actually be discarded. Quit may bypass the untitled guard only after an awaited, single-writer session commit and authoritative losslessness proof; otherwise Cowrite stays open or offers the ratified honest `Quit anyway` override. (D13; CJ 2026-08-27 and 2026-08-28, PR #1833 / issue #1421; appearance: `docs/design/` 9a–9f)
- FR-ED-4 (MUST): Full track-changes suite: CriticMarkup, human/AI attribution, accept/reject (single/bulk/group), prev-next navigation, four display modes (All/Simple/None/Original). (D13)
- FR-ED-5 (MUST): Voice dictation into editor, chat, and comment surfaces (local Whisper; model download/manage; device selection). (D13)
- FR-ED-6: Cut from v1: chat export/search UI, standalone comments panel, AI commit-message button. (D13)
- FR-ED-7 (MUST): External-change detection: if an open file changes on disk (git operation, external editor, agent), offer reload / keep-mine / merge. Once Cowrite observes a divergent revision, it issues no further write to that path until the author chooses: queued/not-yet-issued work is refused, manual and dirty-close Save return attention to the banner, Reload atomically restores the current captured disk side and stays dirty until that write succeeds, Keep mine alone authorizes the next local-content write, and Save As remains separate. Reload's recovery write applies the same FR-ED-2 line-ending normalization as every other save (the per-document CRLF opt-out still applies to it); v1 does not claim byte-for-byte preservation of a foreign editor's line endings on Reload. An atomic save issued before detection may complete; v1 provides no cross-process compare-and-replace against a non-cooperative writer, but its completion cannot replace the captured side or dismiss the unresolved choice. A poll ignores that known Cowrite publication specifically, while a later genuinely external revision becomes the current captured side for Compare, Reload, or Keep mine. Captured recovery bytes are not guaranteed across process loss. If Reload's recovery write itself fails, the buffer keeps the captured disk bytes verbatim, the document remains honestly dirty, and the write pause stays active — only `Try again`, `Save As…`, and Compare may act; `Keep mine` is not offered, because after a Reload the buffer already holds the disk version, so the label would be ambiguous or a no-op. `Try again` resubmits whatever the buffer currently holds (typing is never blocked while unresolved) through the same atomic save path, bounded to one in-flight attempt at a time. (finding #10; CJ architecture amendment #1599, 2026-08-16; failed-Reload action set ruled by CJ, 2026-08-28, #1641/#2074)
- FR-ED-9 (MUST): **Document types.** Cowrite opens, edits, and writes tracked changes into exactly the Markdown family plus plain text: `.md`, `.markdown`, `.mdown`, `.mkd`, `.mkdn`, `.txt` (case-insensitive). These are the types that satisfy D27's two gates: whole-file CriticMarkup safety and an explicitly supported Cowrite editing/projection contract. For every other type, the rail's Documents section has no row, document-open routes (including stale links and restored sessions) refuse visibly with a reason, and Cowrite's editor/tracked-change paths issue no write. A clean legacy unsupported tab closes after that visible refusal. If the restored tab retains unsaved text, the refusal applies to its former path while its exact buffer automatically enters J2's editable untitled recovery surface, visibly labeled by that path; the author may adopt it only through the existing Save As route to a supported document path. The conversion never opens or writes the unsupported source and never treats an omitted over-cap buffer as recovered text (FR-ED-3; D27 amendment, CJ 2026-10-01). **This is a document-boundary rule, not a repo-write allowlist:** D3/FR-AGENT-1/2 still permit direct agent writes to unprotected closed repo files such as skills, logs, indexes, and configuration. Widening the document set is a D27 change, and v1 exposes no user-facing override. `.txt` uses the same source-as-model editor as Markdown (TD-2, FR-ED-1): the file stays the source of truth byte-for-byte, with the knowingly accepted cost that Markdown-looking text appears as Markdown in rich-text view. (D27, D3, D5, D13, FR-X-8)
- FR-ED-8 (MUST): Sidecar data (comments, track-changes) follows its document through rename/move within the project; deleting a document prompts about its sidecar data; a scratch doc saved into the project adopts any comments/changes accumulated while untitled. When Save As adopts an untitled recovery document whose earlier work was omitted, a machine-local event keyed by stable `adoptionId` is durably prepared before the irreversible boundary, promoted only after file success is authoritatively confirmed, and projected exactly once as the D15 adoption timeline card; no document-attached omission field survives adoption. (finding #15; CJ 2026-08-28, PR #1833 / issue #1421)

### 3.6 Cross-cutting requirements

- FR-X-1 (MUST): Cross-platform: macOS + Windows, both tested before release; platform-aware keybindings (Cmd/Ctrl); native dialogs.
- FR-X-2 (MUST): Secrets (API keys, tokens) live only in the OS keychain; never in plaintext, settings files, logs, or exposed to the frontend. All AI/GitHub network calls originate in the backend; the webview itself has no external network egress (CSP `connect-src 'self'`, IPC only — TD-9).
- FR-X-3 (MUST): All agent operations are async, cancellable, and visibly in-progress; agent activity (what it's reading/doing/writing) is observable in the UI, not a silent spinner.
- FR-X-4 (MUST): A project is any folder (D12); one project per app instance (project-open routing: FR-X-10); large documents must not freeze the UI.
- FR-X-5 (MUST): Graceful degradation and clear errors for: CLI not installed, auth expired, rate limited, timeout, offline. Feature availability (git, GitHub, provider) reflects reality, never silently no-ops.
- FR-X-6 (SHOULD): Feedback-to-GitHub-issue flow; theme light/dark/system.
- FR-X-7 (MUST): First-run/onboarding: detect installed CLIs and their auth state (auth-expired ≠ not-installed, distinct remediation); zero providers available = full editor-only mode; provider choice is a per-project default, switchable per conversation. (finding #12)
- FR-X-8 (MUST): Portability contract: the sidecar schemas (`.comments/`, `.track-changes/`) and CriticMarkup usage are documented public formats. Pending CriticMarkup is visible raw on non-Cowrite surfaces (GitHub diff, other editors) — accepted by design on review branches; it never merges to main (D18: clean prose only). (finding #11)
- FR-X-9 (MUST): Account sign-in. GitHub: in-app device-flow sign-in/sign-out with status display (token in OS keychain per FR-X-2); required for collaboration features only (D12). AI providers: auth is owned by each CLI — Cowrite detects signed-out/expired state and guides the user through the provider's own login flow; Cowrite never collects or stores provider credentials itself.
- FR-X-10 (MUST): **Project-open routing.** Every project-open entry point resolves against instance ownership, identically whether or not a run is active: an instance holding no project adopts the chosen project in place; the instance already holding that project stays as it is; a project held by another Cowrite instance is brought to the front; any other project opens in a separate Cowrite instance. Opening a project never refuses, never stops/pauses/migrates a run, and never replaces or tears down the project session (bound MCP server, watchdog, protected set, timeline, tabs) of an instance the user did not ask to leave. At most one live Cowrite instance holds a given project at a time; a lock artifact left by an instance that no longer exists never blocks opening that project. (D26, D12, D21; tech-design §3.5 M7, TD-17)
- FR-X-11 (MUST): **Every project-open request reaches a visible outcome.** Adopted, focused, opened elsewhere, or failed — a project-open action never silently no-ops and never hangs: if the chosen project cannot be adopted, focused, or launched within a bounded time, Cowrite reports the failure and its reason, leaves the choosing instance and the target project exactly as they were, leaves no partial ownership behind, and the user can retry. The same rule governs closing a project: a close request that cannot proceed because a run is active is reported with its reason and leaves the project open — Cowrite offers no stop-and-close shortcut in v1; the user stops the run through the existing run controls (FR-X-3) and closes again. (D26, FR-X-5, UX Principle 7)
- FR-X-12 (MUST): **A routed instance is an ordinary instance.** A Cowrite instance opened by FR-X-10 has full capability and its own tab session (FR-ED-3), run queue (FR-AGENT-7), agent surface, and protected-document boundary (D21/FR-AGENT-2) — nothing shows it was launched by another instance. It is not a child of the launcher: quitting or closing the launching instance never closes it, and no tabs, conversation, queued run, or agent state transfers between instances. (D26, D12)

## 4. Baseline: What the current app does (extracted 2026-07-04)

Functional capabilities of the existing codebase. Each is a *candidate* requirement for the rewrite — kept, changed, or dropped by interview decisions.

### Editor core
- WYSIWYG (Word-like) + raw markdown source view, toggleable; edits sync both ways.
- CommonMark + GFM: headings, emphasis, lists, task lists, tables, code blocks, links, blockquotes, HR.
- **Round-trip fidelity md → rich → md is a P0 invariant.** (Frontmatter currently unverified — gap.)

- Undo/redo (rich view). Inline file rename. Spellcheck.
- Local Whisper dictation into editor, chat input, and comment forms (model download/manage in settings).

- CriticMarkup in the markdown: `{++ins++}`, `{--del--}`, `{~~old~>new~~}` (portable format).
- Attribution sidecar (`.track-changes/`): author, human/AI, timestamp, grouping.
- Accept/reject: single, next/prev navigation, bulk, group-linked (substitutions); 4 display modes (All/Simple/None/Original).
- Gap: AI can't currently produce tracked changes (plumbing exists, unwired).

### Comments
- Anchored to text ranges with snapshot + line/col drift anchors; document-level comments; 1-level threading; resolve; provenance (local vs GitHub-review) and publish status (draft/published) with immutability rules.
- Stored as JSON sidecars (`.comments/`) in the repo.
- "Ask AI" on a thread → streamed reply saved into thread; can carry one `<suggestion>` block the user applies (plain replace, not tracked).

### AI integration
- Providers: Claude (API + `claude -p` CLI pipe), GitHub Models API, Copilot CLI. Streaming + cancel (API only; CLI is single-shot).
- Context assembly: current doc + discovered project files (CLAUDE.md, `.claude/skills/**`, `.claude/agents/**`, copilot-instructions) + user-attached files. CLI runs with repo as cwd.
- Quote-a-selection → anchored chat message → auto-created linked comment; AI reply dual-saved to thread.
- One persisted chat session per document (SQLite, FTS search, JSON/MD export — export/search have no UI).
- Limitation: no agentic capability — the LLM cannot read the repo itself, use tools, or write files; context is manually assembled and size-capped (128KB CLI).

### Collaboration (GitHub)
- Device-flow auth; tokens in OS keychain, never exposed to frontend.
- Git UI: clone, branch list/create/switch, stage/unstage/commit, pull (ff-only), push.
- Per-file "Request Review": auto branch+commit+push+PR+reviewers; sync PR comments → local anchored comments (threaded); accept = squash-merge + cleanup; cancel = close PR. Editing locked during review.
- Publish-local-comment-to-GitHub exists in backend, no UI.

### Platform/infra behaviors worth keeping as requirements
- Secrets only in OS keychain. All AI/GitHub calls from the backend, never the frontend.
- All AI ops async + cancellable with visible progress.
- Feedback-to-GitHub-issue flow. Native menus. Theme light/dark/system.
